# Проверки обмена данными

`corepack pnpm test` запускает быстрые тесты чтения/валидации файлов и защиты
тестового подключения. PostgreSQL для них не нужен. Существующие Google Auth
и session-cookie тесты остаются без дублирования.

`corepack pnpm test:integration` проверяет реальные обработчики приложения:
экспорт → предпросмотр → импорт JSON/XLSX, запись и чтение PostgreSQL,
переназначение ID, иерархию категорий, связи покупок/мест/единиц,
повторный skip после редактирования цены, остатка и форматирования тегов.
Дополнительно проверяются режим add, конкурентный skip, глобальные единицы,
чужие ссылки и подмена владельца, отсутствие записи при ошибке валидации
и полный откат транзакции при искусственной ошибке БД на последней покупке.
Все Excel-файлы для интеграционных сценариев создаются тестами — пользовательские
загрузки не нужны.

## Безопасный запуск

Нужен **отдельный локальный PostgreSQL**, не Development или Production БД.
Роль должна называться `transfer_test`, база — `stockkeeper_transfer_test`.
Роль должна иметь право создавать схемы в этой тестовой БД. Например, на
специально созданном тестовом сервере администратор может выполнить:

```sql
CREATE ROLE transfer_test LOGIN PASSWORD 'transfer-local-only';
CREATE DATABASE stockkeeper_transfer_test OWNER transfer_test;
```

На Linux:

```sh
NODE_ENV=test \
TRANSFER_TEST_DATABASE_URL=postgresql://transfer_test:transfer-local-only@127.0.0.1:5432/stockkeeper_transfer_test \
corepack pnpm test:integration
```

Пароли выше — только примеры для одноразовой локальной тестовой БД.
Настоящие секреты приложения не нужны. Если параметр отсутствует, окружение
не `test`, сервер не loopback, имя БД/роли другое или в URL есть дополнительные
параметры, запуск завершается ошибкой **до подключения**.
`DATABASE_URL`/`EXTERNAL_DB_URL` никогда не используются как запасной вариант.
Дочерний процесс получает только разрешённые переменные окружения, без секретов
приложения, SMTP или интеграций.

Каждый прогон создаёт случайную схему `transfer_test_<uuid>` и генерирует SQL
из текущей Drizzle-схемы. Runtime pool и хранилище сессий работают только в ней;
это проверяется до создания аккаунтов. В конце удаляется только схема этого
прогона. `public`, пользовательские таблицы и данные не очищаются:
нет `TRUNCATE`, удаления базы, автоматического `push` или `push-force`.
Если процесс аварийно остановлен, может остаться его тестовая схема; следующий
прогон использует новую, а не пытается очистить старую.

В `.github/workflows/ci.yml` отдельный job **Backup restore (PostgreSQL)** создаёт
одноразовый PostgreSQL 17 service с фиксированными тестовыми реквизитами. Job
не читает GitHub Production Secrets, не меняет окружение публикации и не запускает
DDL при старте/сборке приложения. Ошибка любого интеграционного сценария
завершает job с ненулевым кодом. Отсутствие тестовой БД — ошибка, а не skip.

## Подтверждение импорта в браузере

`corepack pnpm test:browser` запускает Chromium через Playwright, настоящее
React-приложение и API на случайных loopback-портах с той же защитой подключения
и новой случайной схемой из `helpers/transfer-test-database.mjs`.
Не направляйте сценарий на открытое приложение, Development или Production:
адрес приложения вычисляется самим тестом, параметра внешнего base URL нет.
Vite proxy используется только внутри теста, настройки рабочих сервисов не меняются.

После установки зависимостей подготовьте браузер:

```sh
corepack pnpm --filter @workspace/inventory-app exec playwright install chromium
```

На Linux, если требуются системные библиотеки Chromium, используйте
`playwright install --with-deps chromium` на поддерживаемом дистрибутиве.
В Replit/NixOS можно использовать уже установленный Chromium, передав
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/repl/tools/bin/chromium`.

Запуск на отдельной тестовой БД:

```sh
NODE_ENV=test \
TRANSFER_TEST_DATABASE_URL=postgresql://transfer_test:transfer-local-only@127.0.0.1:5432/stockkeeper_transfer_test \
corepack pnpm test:browser
```

В Windows PowerShell задайте эти две переменные через `$env:NODE_ENV` и
`$env:TRANSFER_TEST_DATABASE_URL`, затем выполните `corepack pnpm test:browser`.
Пароль выше — пример только для одноразовой тестовой БД.

Сценарии находятся в
`artifacts/inventory-app/tests/data-exchange.browser.test.mjs`. Для каждого
формата JSON/XLSX создаются три изолированных аккаунта, вход выполняется настоящим
парольным API (без Google), а cookie передаётся новому браузерному контексту.
Файлы создаются экспортом синтетических данных в памяти; `attached_assets/`
и пользовательские загрузки не читаются. Сетевые обращения вне loopback-приложения
блокируются. Дочерний процесс не получает секреты приложения, а Vite не читает
проектные `.env` (используется пустой временный каталог).

Проверяются:

- preview не вызывает import и не записывает данные; без галочки import недоступен;
- выбор другого файла немедленно убирает предыдущий preview, сбрасывает галочку
  и режим add; новый preview и итоговая запись относятся к новому файлу;
- во время import кнопка, выбор файла, галочка и режимы недоступны;
- настоящая поздняя ошибка PostgreSQL откатывает запись, показывает ошибку
  и сохраняет preview/подтверждение для явного повтора;
- повтор отправляет те же данные/режим; успех показывает все счётчики,
  убирает ошибку/preview и обновляет активный запрос;
- ранее открытые списки товаров и покупок показывают новые записи после
  SPA-перехода без перезагрузки; исходный и посторонний аккаунты не изменились.
- повторная загрузка той же копии проверяет radio → mode в запросе → счётчики:
  skip показывает 3 пропуска и не меняет ни одной записи, add создаёт по одной
  дополнительной копии каждого товара и покупки без дублирования справочников;
  оба режима повторно обновляют ранее открытые списки без reload.
- отдельные JSON/XLSX-сценарии на телефоне 390×844 (touch/mobile) проверяют
  подтверждение, выбор skip/add и все счётчики; переходы используют нижнюю панель
  и выдвижное меню, а не скрытый desktop sidebar. После первого импорта и
  повторного skip видны ровно 2 карточки товаров и 1 покупка, после add — 4 и 2.
  Считаются сами карточки, проверяются оба названия товаров, отсутствие reload
  и сохранность оригинальных записей/данных других синтетических аккаунтов.
- отдельные JSON/XLSX-сценарии с `locale: ru-RU` используют штатное определение
  языка (без подмены i18n/localStorage) и подписи из `src/i18n/locales/ru.json`
  приложения inventory-app. Проверяются русские названия предпросмотра,
  обязательного подтверждения, режимов skip/add и все счётчики до/после импорта;
  товары и покупки открываются через русские ссылки без reload. Повторный skip
  не меняет записи, add сохраняет оригиналы и добавляет ровно одну копию.

## Сохранённый язык в браузере

Тот же `corepack pnpm test:browser` запускает
`artifacts/inventory-app/tests/language.browser.test.mjs`. Общий
`tests/helpers/browser-harness.mjs` приложения inventory-app поднимает/закрывает
Chromium, Vite и API; каждому тестовому файлу выделяется новая случайная схема
в той же защищённой loopback-БД. Дополнительные секреты или команды не нужны.

Для en-US и ru-RU проверяется выбор ru/en/auto через штатные настройки:

- явный русский при английском locale и явный английский при русском;
- тело и ответ PATCH, сохранённое значение в PostgreSQL и auth/me,
  localStorage и выбранная кнопка настройки;
- переведённые заголовки, кнопка сохранения и Sidebar; переходы по спискам
  и возврат в настройки, затем reload;
- парольный API-вход в новом браузерном контексте без унаследованного
  localStorage: сохранённый язык берётся с сервера. Противоположный locale
  не меняет ru/en, но меняет язык интерфейса для auto;
- auto после явного выбора, противоположного locale: override снимается,
  а предпочтение остаётся именно auto после reload, logout и повторного входа;
- смена двух аккаунтов в одном mobile/touch-контексте 390×844 через выход
  в выдвижном Sidebar и парольный API-вход без очистки localStorage:
  серверные ru/en/auto нового пользователя заменяют предыдущие настройки,
  email, нижнюю панель и меню. SPA-возврат с удержанными фоновыми GET профиля
  проверяет новый React Query-кэш без перезагрузки документа;
- отсутствие необработанных ошибок браузера и изменений данных своего/чужого
  аккаунтов. Только синтетические аккаунты; Google sign-in не выполняется,
  внешняя сеть блокируется, `.env` и пользовательские загрузки не читаются.

В CI браузерные сценарии идут после API-регрессии в job **Backup restore
(PostgreSQL)** на одноразовом PostgreSQL service. Отсутствие Chromium/БД, ошибка
браузера или неуспешная проверка завершают запуск с ненулевым кодом, без skip.
При обычном завершении и неуспешной проверке закрываются браузер/API/Vite,
удаляются временный каталог и только случайная схема текущего прогона.
При принудительном завершении процесса схема может остаться, как и в API-тестах.
